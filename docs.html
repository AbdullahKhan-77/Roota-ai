GETTING STARTED

Introduction

Roota is an AI-native production debugger that connects your crash logs to your actual source code and delivers exact root causes, timelines, and fixes — automatically.

ℹ️
Roota is currently in beta. The CLI, Python SDK, and C++ handler are all fully functional. Web UI and API access require a free account.

Most debugging tools tell you what broke. Roota tells you why and how to fix it — by reading your actual codebase, not making generic guesses.

How it works

When you analyze a log file, Roota:

  1. Parses and structures all errors and warnings from your log
  2. Extracts which source files are mentioned in the crash
  3. Fetches the actual source code from your GitHub repository
  4. Sends logs + real source code to AI for grounded analysis
  5. Returns an exact diagnosis: root cause, timeline, cascading effects, and fix

CLI Overview

The Roota CLI is the fastest way to analyze a log file. It runs entirely on your machine and doesn't require the server to be running.

python debugai.py [OPTIONS]

analyze command

The primary command. Analyzes a log file and returns an AI-powered diagnosis.

# Basic analysis
python debugai.py --log crash.log

# With GitHub source code (recommended)
python debugai.py --log crash.log --repo owner/repo-name

# With C++ crash report
python debugai.py --log crash.log --repo owner/repo --crash-report crash_report.log

Options reference

OptionRequiredDescription
--logYesPath to the log file to analyze. Supports any format — structured, JSON, Python tracebacks, etc.
--repoNoGitHub repository in format owner/repo. Enables exact line-level diagnosis using real source code.
--crash-reportNoPath to a C++ crash_report.log generated by the Roota crash handler. Enables exact memory address resolution.
--versionNoShow the current version.
--helpNoShow help text and exit.

Python SDK

The Python SDK automatically captures unhandled exceptions and sends them to your Roota server for analysis. No manual log uploads needed.

Setup

Copy debugai_sdk.py into your project, then add two lines:

import debugai_sdk

debugai_sdk.install(
    repo="owner/your-repo",
    server="http://127.0.0.1:8000"  # your Roota server URL
)

How it works

The SDK installs a global exception handler using sys.excepthook. When any unhandled exception occurs:

  1. The full stack trace is captured automatically
  2. It's formatted into Roota's log format
  3. Sent to your server's /ingest endpoint via HTTP POST
  4. Your server analyzes it and stores the incident
  5. The normal Python traceback is still printed to the terminal
✅
The SDK works with any Python app — Django, Flask, FastAPI, scripts, or long-running services. Add it once at startup and every crash is automatically captured.

Configuration options

ParameterDefaultDescription
repoNoneGitHub repo (owner/repo) for source code fetching. Optional but strongly recommended.
serverhttp://127.0.0.1:8000URL of your Roota server instance.

C++ Crash Handler

A header-only, binary-agnostic crash handler for C++ applications. Drop it into any project — no build system changes required.

Setup

Copy cpp_integration/debugai_handler.h into your project:

#include "debugai_handler.h"

int main() {
    debugai::install_crash_handler("logs/");  // output directory
    
    // ... rest of your application code
    return 0;
}

Compile with debug symbols

g++ -g your_app.cpp -o your_app
⚠️
The -g flag is required. Without debug symbols, Roota cannot resolve memory addresses to source lines.

What gets captured

When your application crashes with a segmentation fault (SIGSEGV), the handler automatically writes a timestamped crash report:

logs/crash_report_20260615_143022.log

Containing:

BASE_MAP: 60b82188b000-60b82188d000 r--p 00000000 ... /path/to/your/binary
SIGNAL: 11
CRASH_ADDRESS: 0x60b82188d451

Analyze the crash

python debugai.py --log service.log \
    --repo owner/repo \
    --crash-report logs/crash_report_20260615_143022.log
ℹ️
C++ crash analysis requires WSL (Windows Subsystem for Linux) on Windows, or a native Linux environment. addr2line must be installed (sudo apt install binutils).

POST /analyze

Analyzes a log file and returns an AI-powered diagnosis. Requires authentication.

Request

POST http://127.0.0.1:8000/analyze
Content-Type: multipart/form-data
X-API-Key: your_api_key

log_file: <file>
repo: owner/repo-name  (optional)

Response

{
  "status": "success",
  "incident_id": 42,
  "stats": {
    "total_lines": 8,
    "errors": 5,
    "warnings": 2
  },
  "errors": [...],
  "warnings": [...],
  "diagnosis": "INCIDENT SUMMARY: ..."
}

POST /ingest

Receives crash data from SDKs and auto-capture handlers. Used by the Python SDK automatically.

Request

POST http://127.0.0.1:8000/ingest
Content-Type: application/json

{
  "log_text": "2024-03-10 ERROR [Service] ...",
  "repo": "owner/repo",
  "source": "python_sdk"
}

GET /incidents

Log Formats

Roota's parser handles any log format automatically using a two-stage approach:

Stage 1 — Regex parser (fast, free)

Handles the standard structured format:

2024-03-10 14:22:01 ERROR [UserService] KeyError: 9981

Stage 2 — AI parser (any format)

If fewer than 2 lines match the regex, Roota automatically falls back to AI parsing, which handles:

  • Python tracebacks
  • JSON structured logs
  • Node.js / Winston logs
  • Java / Log4j logs
  • Nginx error logs
  • Any custom format

GitHub Integration

When you provide a --repo argument, Roota fetches your actual source files from GitHub to produce grounded diagnoses with exact variable names and line references.

File disambiguation

Real codebases often have files with the same name in different folders. Roota uses a three-stage pipeline to find the correct file:

  1. Filename match — find all files matching the name from the log
  2. Test file filter — prefer non-test paths for production crash analysis
  3. Function verification — fetch candidate files and check which one contains the function named in the traceback
ℹ️
Roota automatically detects your default branch — works with main, master, develop, or any other branch name.

C++ Crash Analysis

C++ production crashes produce raw memory addresses, not human-readable stack traces. Roota resolves these addresses to exact source lines using addr2line.

The pipeline

  1. Your app crashes → signal handler captures BASE_MAP and CRASH_ADDRESS
  2. Roota calculates: file_offset = crash_address - base_address
  3. Runs: addr2line -e your_binary 0xoffset
  4. Gets: source_file.cpp:line_number
  5. Fetches that file from GitHub and produces a 10/10 confidence diagnosis
⚠️
C++ crash analysis requires binaries compiled with -g debug symbols. Stripped production binaries will produce lower confidence diagnoses.
